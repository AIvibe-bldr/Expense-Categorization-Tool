# 本番接続と運用

## 本番化の前提

ローカル検証は完了可能ですが、本番Supabase・Google OAuth・公式CSVでの受入検証は別途必要です。金融API自動取得は有効化していません。金融サービスへの送金・振込・決済操作は実装していません。

## Supabase

1. 非公開のSupabaseプロジェクトを作成し、`supabase/migrations/202610220001_expenses.sql` をマイグレーションとして適用します。
2. Authで利用者を作成します。必要に応じて公開サインアップを無効にします。本UIは管理者が登録済みのメール・パスワードでログインします。銀行のログインパスワードではありません。
3. ホスティング環境の秘密管理で下記を設定します。値をGit・チャット・ログに貼らないでください。

| 変数                          | 用途                                                                    |
| ----------------------------- | ----------------------------------------------------------------------- |
| GALAPAGOS_LOCAL_MODE=0        | 本番では認証必須                                                        |
| NEXT_PUBLIC_SUPABASE_URL      | 自分のプロジェクトURL                                                   |
| NEXT_PUBLIC_SUPABASE_ANON_KEY | 公開可能なanon/publishableキー。RLSは必須                               |
| DATA_ENCRYPTION_KEY           | 32バイト乱数をBase64にした値。原本・状態・トークンをAES-256-GCMで暗号化 |
| APP_ORIGIN                    | 実際のHTTPSオリジン。末尾スラッシュなし                                 |
| SUPABASE_SERVICE_ROLE_KEY     | 日次ジョブのみが使用するサーバー専用キー                                |
| CRON_SECRET                   | 日次エンドポイント用32文字以上のランダム値                              |

鍵は秘密管理基盤で生成・保管します。ローカル開発では `.local/encryption.key` が権限0600で生成されます。プロキシがHTTPS送信時に置換するプレースホルダーをローカル暗号鍵として使うことはできません。`DATA_ENCRYPTION_KEY` にはアプリプロセスで使える実鍵が必要です。

4. `npm ci`、`npm run build`、`npm start`。リバースプロキシでHTTPSを終端し、Node.jsのループバックポートへ接続します。リクエスト制限・レート制限・監視はホスティング側でも設定します。
5. ユーザーA/Bでログインしてそれぞれ取込を行い、他ユーザーの状態・原本・バックアップにアクセスできないことを実プロジェクトで確認します。未認証APIが401、外部Originの変更要求が403になることも確認します。

RLSは全テーブルで有効です。更新は所有者を `auth.uid()` から取得するRPCで、楽観ロックとDBトランザクションを使用します。service_roleはブラウザーに渡しません。日次RPCはauthenticated/anonから実行できません。

この実装の正本は所有者ごとの暗号化状態です。独立した `transaction_records` に暗号化した共通形式取引を保持し、`expense_history` に全更新世代を保持します。金額や利用先をクライアントから直接SQL検索する設計ではありません。少人数・個人運用向けです。大規模化時は履歴の保存期間・ページング・ジョブキューと、鍵管理を含む正規化DBへの移行を別途設計してください。

## Google OAuth / Sheets

1. Google CloudプロジェクトでGoogle Sheets APIを有効化します。
2. OAuth同意画面を設定し、テスト段階では利用者をテストユーザーに追加します。
3. OAuth「ウェブアプリケーション」クライアントを作成します。
4. 承認済みリダイレクトURIを正確に `APP_ORIGIN/api/google/callback` に設定します。ローカル検証も同じホスト・ポートで登録します。
5. `GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET` を安全なサーバー環境変数に設定します。
6. UI「サービス連携」→「Googleで認証」。`spreadsheets`スコープとオフラインアクセスを使います。OAuth stateは暗号化・所有者照合・10分期限・一回使用です。refresh_tokenはDBに暗号化保存します。
7. 自分が編集できる専用スプレッドシートを作成し、IDを入力して保存・手動同期します。
8. 元CSVと、DB件数、8種類のシート、購入支出合計、AO列以降のメモ保持を確認します。更新を2回実行して行が増殖しないことを確認します。

接続先: `accounts.google.com`、`oauth2.googleapis.com`、`sheets.googleapis.com`。Supabaseは自分のプロジェクトのホストを追加します。権限エラーやネットワーク拒否がある場合は連携済みとは扱いません。

OAuthテストモードのrefresh_token有効期間等はGoogle側の現行規約に従います。期限切れ時は再接続してください。認証エラー時も取引DBは保持されます。

## 日次同期

外部スケジューラーから1日1回、`POST /api/jobs/daily` を実行し、秘密ヘッダー `Authorization: Bearer <CRON_SECRET>` を付けます。例: 日本時間06:00に更新したい場合はUTC21:00に設定します。実トークンをコマンド履歴や公開リポジトリに記載しないでください。

日次処理はDBを正本としてSheetsを更新します。CSV方式の金融明細を銀行から自動取得する処理ではありません。Supabase service_roleで所有者を列挙し、各所有者の暗号化Googleトークンで更新します。同一所有者の同期は30分のリースで排他します。異常終了でロックが残った場合は失効後に再実行します。大規模データで30分を超える可能性がある運用では、ジョブ分割・リース更新を追加してください。

HTTP 503のジョブ失敗をスケジューラーから通知する設定にします。アプリ内にも同期エラー・最終成功日時・未同期状態を表示します。メール通知は本実装には含みません。

## バックアップ・復旧

- 本番DB: Supabaseのバックアップ/PITRを契約プランに合わせて有効にし、日次の取得と復旧演習を行います。
- ローカルDB: 起動中のSQLiteファイルだけを直接コピーするとWALが欠落します。停止してDB/WALを含む `.local` 全体を安全に保管するか、SQLite Backup APIを使用します。
- UI: 所有者付きAES暗号化バックアップをダウンロードできます。復旧は同一所有者・同一暗号鍵のみ。不足明細・バッチ・対応する照合記録を追加します。
- 全時点復旧: DBと暗号鍵を合わせてステージングに復元し、件数・金額・原本復号・照合状況を検証後に切替えます。画面の「不足明細復旧」は時点ロールバックではありません。
- `expense_history` は世代履歴であり、別障害ドメインのバックアップの代わりではありません。
- 鍵の変更だけでは既存データを復号できなくなります。鍵ローテーションは停止・全暗号列の再暗号化・復旧検証を伴う別作業です。

## 本番受入チェック

実CSV5種で件数・金額・返金・手数料・請求月を照合、同じCSV再取込、別月の重複CSV、カード・銀行の対応、PayPayチャージ、分割・リボ・取消の確認、Google実同期、RLS実認証2ユーザー、バックアップ復旧を実施してください。既存売上ツールを接続する場合は、その別リポジトリで回帰試験を実施してください。
