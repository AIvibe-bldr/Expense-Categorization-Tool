# 利用・運用マニュアル

## 1. 初回の取込

1. 「サービス連携」で金融サービスを選びます。
2. 口座別名を指定します。例 `chiba-main`、`sbi-main`、`rakuten-main`。実口座番号・ログイン情報は不要です。別の口座・カードを同じ別名で取り込まないでください。
3. 公式サイトから自分で取得したCSVを選択します。UTF-8かShift_JISを選びます。5MB・20,000行が上限です。
4. 認識できないヘッダーは「列対応」で指定します。下記の共通項目を任意のCSV列に対応付けます。
5. 手数料列がある場合は出金額に「含まれる」か「別払い」かを確認します。未指定では金額を推測せず取込を停止します。
6. 取り込み後、履歴の新規件数・重複件数と元CSVを比較してください。不正な行があれば全体を保存せず、行番号付きで通知します。

同じファイルの再アップロードは再登録しません。明細IDがある場合はサービス・口座別名・明細IDで重複を判定します。同じIDで金額・日付等が変わるデータは自動上書きせずエラーになります。

**明細IDがないCSV**は日付・正規化利用先・金額・方向・種別・カード・請求月・支払区分・同一内容の出現回数で指紋を作ります。一つのCSV中の同額2件は2件保持します。別ファイルの既存行との一致は確認なしで除外しません。内容を比較した後、「指紋による重複除外」を承認して再実行してください。同日・同額・同店の実在する別取引を含むなら、統一した固有明細IDを付与したCSVで取り込んでください。

### 列対応

```json
{
  "date": "お取引日",
  "merchant": "摘要",
  "outflow": "お引出し金額",
  "inflow": "お預入れ金額",
  "id": "取引番号"
}
```

| 共通項目           | 内容                                                       |
| ------------------ | ---------------------------------------------------------- |
| date / posted_date | 取引日 / 計上日。YYYY-MM-DD、YYYY/MM/DD、年月日等          |
| merchant           | 利用先・摘要。必須                                         |
| amount             | 金額。正数は出金、負数は入金。返金種別は入金として扱う     |
| outflow / inflow   | 銀行の出金額 / 入金額。片方のみ正数                        |
| type               | 取引種別。下記のいずれか                                   |
| id                 | サービスが付与する一意の明細ID                             |
| billing_month      | 請求月 YYYY-MM                                             |
| debit_date         | 引落予定日                                                 |
| statement_amount   | 月の請求確定額。個別利用額ではない                         |
| card_id            | 同一カードを識別する別名。銀行引落にも同じ値を指定         |
| counterparty       | 自己口座間移動の相手口座別名                               |
| reference          | 両側で一致する、確認済みの決済参照番号。適当な値を入れない |
| installment        | 分割・リボ情報。入っている場合は自動確定せず確認待ち       |
| balance / fee      | 取引後残高 / 振込手数料                                    |

取引種別: `購入`、`店舗決済`、`支払い`、`返金`、`カード引落`、`自己口座振替`、`送金`、`残高移動`、`チャージ`、`入金`、`手数料`、`元本返済`、`投資`、`税金`、`引落不能`、`取消`、`その他`。英語の内部enumも使用できます（`src/lib/types.ts`）。

カードの種別未指定は正数を購入、負数を返金とします。銀行・PayPayの未知の種別は未判定です。銀行摘要が楽天カード・三井住友カード・PayPayを示す場合は引落・チャージ候補にしますが、照合は未確定です。PayPayの「チャージ」を購入に変更しないでください。

## 2. 分類する

取込時に分類・項目を確定できない明細は「その他」に仮置きし、月ごとの「未分類確認」にまとめます。金額はその月の購入支出に含まれますが、分類は確認待ちです。「未分類確認」→「詳細・分類」で用途を選びます。候補は未確定です。商品明細がないAmazon等の用途をシステムが断定することはありません。

- 利用先分類: Amazon、コンビニなど、どこで買ったか。
- 用途分類: 元Excelの分類。何のために使ったか。
- 事業/個人: 初期値は未判定。税務上の必要経費とは別です。
- 「次回も適用」: 正規化後の利用先が完全一致する新規取引に、承認済み用途を適用します。

「分類管理」では分類とその中の項目を追加し、既存の名前や項目の所属分類を変更できます。IDは維持され、項目の所属変更は既存取引の親分類にも反映されます。承認済み利用先ルールの編集・削除は将来の取込に適用します。過去明細を無断で一括変更しません。

月別経費表では元年度を表示しません。分類選択肢では同名を識別するため元年度とセル位置を表示します。同じ「所得税」や「交通費」でもIDは異なります。分類マスターの親と小計は取引の分類先にできません。

## 3. 照合する

カード購入は利用日に計上し、銀行引落は資金移動として購入支出から除外します。銀行出金には実際の引落額が残ります。

自動確定にはカードID・請求月・予定引落日・請求確定額・取得済み明細の合計が必要です。同額であっても他の情報が不足すれば確認待ちです。分割・リボは請求書で確認してください。月の請求額と購入全額が異なるので、単に一致させるための金額変更はしないでください。

銀行振替・チャージの自動確定には逆方向の明細、同日・同額、両口座の対応、共通参照ID、候補の一意性が必要です。日付がずれる振替は手動で対応付けます。

PayPay/カードの同一購入は共通参照IDがなければ候補表示のみです。暫定集計には両方が残ることがあるため、確定前の合計には使わないでください。ユーザーが根拠を入力して確定するとPayPay側を除外し、原本は残します。

「手動で対応付ける」ではカードの複数明細と銀行1件も選択できます。購入と利用取消は同一口座の同額2件を選び、取消証憑を確認してから確定します。返金データもある場合は取消との二重調整を避け、実際の請求に沿ってどちらを適用するか確認してください。

### 例外

- 未取得・一部取得・同額の複数候補: 確認待ちのまま保持。
- 分割・リボ: CSVにある金額は暫定表示。元の購入額・請求元本・手数料の切り分けが確認できるまでは確定しない。未知の返済スケジュールは生成しない。
- 返金: 返金日の月の購入支出を減額。過去月の購入は改変しない。
- 引落不能: 銀行出金にも購入支出にも含めない。再引落は別明細として保持して手動確認。
- 手数料: 手数料自体は購入支出。自己口座振替の元本とは分ける。
- 税金・投資・元本返済: 銀行出金として把握し、購入支出・税務経費には自動算入しない。

## 4. Google Sheets

Googleで認証し、専用スプレッドシートのIDを保存します。初回は手動同期を実施します。以後、取込・分類・照合の保存後に更新します。日次更新は管理者がジョブを設定する必要があります。

8種類の出力: 経費サマリー、対象年 月別経費、カード明細、PayPay明細、銀行入出金、未分類・確認待ち、重複・照合、分類マスター。取引がある過去年の月別経費も更新します。

**A〜AN列はシステム専用。手動メモ・設定はAO列以降または別シートへ保存してください。** 行の増減により取引行が変わるため、重要なメモは取引IDをキーに別シートで管理すると安全です。既存の同名シートは管理印がない限り上書きせずエラーにします。分類マスターシートを編集してもDBには逆同期しません。

同期は繰り返しても同じ管理範囲を置換するため行が増殖しません。Googleの8シート全体に跨る原子性はありません。途中エラーはDBに記録して通知し、再実行で収束します。更新中の表は確定資料に使用しないでください。

## 5. バックアップ

「暗号化バックアップ」で取得します。暗号鍵が失われると復号できません。鍵は別の秘密管理基盤へ保管します。

画面の復旧は不足明細・取込バッチ・対応する照合記録を追加する方式で、既存明細を削除・上書きしません。分類ルール・照合・設定を含めた時点復旧は、DB全体のバックアップから管理者が実行してください。復旧後には合計と原本件数を照合します。
